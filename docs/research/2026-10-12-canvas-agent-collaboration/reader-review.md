# 方案独立读者审阅

日期：2026-10-12。审阅对象：`基于画布的Agent成果协作方案.md` v0.1。

审阅方式：只阅读该方案（含审阅期间补充的既有文稿 owner 与版本边界内容），未阅读研究附录、源码或本聊天历史；未运行五个项目、Nomi 或任何推荐组件。本报告检验方案自身的可理解性、内部一致性和决策充分性，不确认源码事实、许可证适用结论或产品行为。OpenDesign 段尚在补充，不将其缺席作为问题。

总体判断：方案已足以讨论“是否批准 P0 探针”，尚不足以作为 M1 实施合同。核心方向、复用原则与未实施状态清楚；最影响下一步的缺口是确认后的版本语义、跨版本锚点的授权边界、原生文稿的结构版本保证，以及文件成果/评论 owner 的实际落点和 P0 出口证据。没有发现它把 Office 保真、CRDT 或稳定 id 直接宣传为已解决能力。

## 1. 用户解决什么，与 Nomi 的关系是否清楚

清楚。用户面对的具体摩擦是：已经看到 Agent 的成果，却必须在聊天里重复解释“哪一份、哪一处、什么不满意”，修改后还难确认 Agent 是否只改了授权范围。方案以“选择对象 → 提问题 → 显式执行 → 看差异 → 验收或撤回”闭环解决它。

与 Nomi 的关系也清楚：第一落点围绕现有视频项目的脚本、提案、参考网页和制作说明，复用画布组织与创作上下文。没有把通用办公、网页 IDE 或多人白板当作首版必需品。第 9 节把“反馈成本下降”写成待测假设，有基线、有真实素材、有阻断项。

仍建议明确一个首要用户和首个必做任务，例如“独立视频创作者向客户交付提案并连续修改三轮”。当前列出的成果种类较多，“真实多成果提案”也容易在 P0 被误解为必须跨格式交付。建议在 P0/M1 各写一行唯一主任务，其余作为评测样本或后续需求。

## 2. 五项目各学什么，直接复用与借鉴是否分清

分得清，且没有任何项目被当成完整可接入的底座。

| 项目 | 主要学习对象 | 当前直接复用结论 |
|---|---|---|
| Doop | 元素上反馈、讨论与执行分开、选择桥与工具闭环 | 应用代码仅评估小段移植，不是评论 SDK；许可与来源须审查 |
| Onlook | 视觉对象稳定身份、DOM 与源码/组件实例映射 | 首版只学身份原则；正式 React 工程需求成立后才评估 parser 移植 |
| AFFiNE | 同内容多视图、分型评论锚点、局部读取与 diff | 借鉴边界，不搬 BlockSuite/Lit/Yjs/DI |
| OpenCanvas | 类型注册、每种成果的受约束读改动作 | 接既有 capability registry，不引第二套 tldraw 或万能插件平台 |
| HugAgentOS | 文件生成、存储、预览和导出分层 | 优先直接使用其采用的上游组件，不移植整个应用 |

“主要复用成熟 npm 组件与 Nomi 既有能力”的结论明确。建议把 Doop 行的移植条件写得更严谨：保留许可证声明只是必要动作之一，接入决策还须确认相应许可证义务是否与 Nomi 的分发方式相容。该提醒不构成法律核验结论。

## 3. 推荐首版组件与不自研范围

读者可以复述首版组合：React Flow + Tiptap/ProseMirror + 既有 pi/lane host + TargetRef/PreconditionSet + 资产/预览/提交链 + Zod。Unique ID 是需验证的候选，不是已经装好的能力；图片区域需求成立才加 Annotorious。morphdom、JSON Patch、Office 相关库不应因为列进选型表而自动进入 P0。

明确不自研的范围覆盖富文本、无限画布、位置变换、Office 解析渲染、公式、DOM diff、Agent 会话/重试/压缩/存储。第 7 节还承认评论锚定、桥和事务本身是通用问题，不能改名后称领域算法，这一点很好。

仍有一个可执行性缺口：“接线”也可能渐渐长成新框架。建议 P0 产物增加一张复用对照表：每个新增模块对应的现有 owner/public API、为何不能直接调用、允许新增的职责、明确不包含的通用能力。尤其覆盖评论线程持久化、候选提交、恢复、command id 去重和 HTML 选择桥。无需在方案里先指定文件实现，但应在 P0 出口禁止出现第二套队列、history、event log 或通用 transaction coordinator。

## 4. 身份、版本、评论与 Agent 状态的唯一 owner

概念所有权总体清楚：已有文稿继续由 workbenchDocuments.contentJson/documentSessionPort 持有，成果视图只引用 documentId；项目 owner 持文件成果逻辑记录、评论和确认；资产 owner 持字节；Run 持生产来源与花费；pi 持会话执行事实；界面与线程只投影状态。方案明确不复制正文或成果数据库，不把普通文档塞进 ProductionRun，也不让 UI undo 抹掉供应商事实。

文稿 owner 的实际入口已经给出；文件成果/评论的准确代码 owner 落点仍待 P0 door-map 明确。方案已经承认这一点，因此不能说它“没有意识到 owner”，但也不能称它完成了架构落地设计。Mermaid 的“项目 owner：不可变文件与成果元数据”把字节 owner 和元数据 owner 合在一个框，且将文稿也画进文件发布/切换引用的统一路径，与正文按类型 owner 的结论不完全一致。建议图分成文稿原生事务与文件发布两个分支，再汇合到回执/界面。

需要补三项约束：

1. 用户确认归属哪个 revision/批次？确认后人或 Agent 再改，原确认必须保留为历史事实，当前版本重新待验收，不能继续显示整份成果“已确认”。
2. 同一成果有两个并发候选时谁先提交、另一项如何失效？期望版本检查已有方向，但需明确失败项保留候选、重新读当前版本、不得自动重放旧意图。
3. Run 来源成果经普通编辑后，Run artifact 的生产快照与逻辑成果的 currentRevision 如何关联？建议 Run 产物保持不可变来源快照，后续修订只在成果记录推进；若反向发布回 Run，另走既有受控入口。这是建议，需要 P0 查明现有合同后确定。

## 5. 第一阶段的范围与验收是否具体

P0 范围相对克制：一份文档、一份受控静态 HTML，验证同一成果引用、带版本选择、现有 owner 的修改/恢复/撤回。M1 才扩大成连续多轮闭环；M2/M3 有条件后置。第 9 节的真实素材、12 任务 × 3 轮、聊天基线、静默错目标/过期覆盖/损坏/重复生成阻断项，比泛泛的“体验顺畅”具体。

但 P0 的出口证据仍略松：第 9 节是方向试点验收，容易被当成 P0 全部必须做，也可能反过来只交探针报告便宣布 P0 通过。建议新增 P0 专用表，逐行标“必须通过/允许 unverified/失败即停”，至少包括：

- 同一成果在画布/专注视图/重启后 identity 与 revision 一致。
- 文档重复文本、HTML 同类卡片插入后，选择和实际修改仍对应正确目标；不确定即拒绝。
- 选择后发生人工编辑，旧候选提交不得覆盖；重定位必须重新捕获当前 revision。
- 一次批量修改对应一个可辨认撤回单元；重启后仍能撤回，已确认事实按版本保留。
- 在候选发布前、字节发布后但引用切换前、引用切换后分别故障注入，重开只恢复唯一提交结果，原资产可读；不能把中途状态显示成功。
- 连点、取消和重启不产生重复执行或重复生成；真实调用状态不明时明确待核实。
- 真 Electron 的受限 HTML 桥、焦点和销毁有效；未验证的平台明确列出，不能用单平台结果过所有平台门。

完整视觉候选、用户确认后的 board 和精确 owner/module 清单应当是 M1 开工前出口。P0 探针允许先取得必要技术证据，但不能以 exploration 代替已批准界面合同。

## 6. 是待评审还是已实施

非常清楚是待评审。开头、设计卡和末尾都声明本轮未改产品、组件未接入、五项目未运行、无实现 commit/PR/产品验收收据；“已有”与“建议”也有专门定义。没有把本报告或源码阅读当产品独立验收。

建议下一版继续保持此状态标识，并在引入新项目后同步开头数量、章节标题与末尾说明，避免局部更新造成范围不一致。

## 7. 影响决策的欠缺、歧义和过度承诺风险

### A. 人确认之前何时写入：主体答案已有，但名称仍容易误导

第 2 节明确默认是用户点击执行后，工具校验合格即进入当前工作版本，标待确认；用户确认是验收，不是保存。这已经回答最关键问题，无需再次要求用户选“先保存还是先确认”。

但第 10 节把发布后的状态叫“候选待确认”，文案又叫“已生成候选 / Changes ready”，而前文“候选”也指尚未发布的临时内容。建议区分两个事实：未提交候选与已应用待验收。前后差异、取消按钮、撤回按钮必须据实际提交事实显示。并补“用户点不满意”是仅留下反馈、还是立刻撤回；建议默认保留当前已应用版本并给一键撤回，避免把验收评价隐式变成写入动作。

### B. 跨版本锚点：可靠映射与过期写入之间应有明确规则

方案同时说“版本已变化则冲突”与“可靠映射则跟随”。两者可以兼容，但尚未写清：展示位置跟随不等于旧执行授权自动延长。

建议明确：已保存评论可映射到新版本用于展示；自动执行仍绑定用户提交时捕获的 revision。版本发生变化时，即使锚点能显示在新位置，也先拒绝旧候选，展示变更并重新确认范围/提交。跨版本映射需有连续的事务映射或受控对象变更记录；重启后没有映射链、全文替换、导入和外部改写等情况就把旧锚点标失效，而非凭引文相似度授权写入。

当前仅提 ProseMirror Mapping，还没有说映射链是否持久化、如何跨重启取得、撤回后如何恢复评论。不能从“有 Mapping”和“稳定 block id”推出这些问题已经解决；这应列为 P0 关键探针。

### C. 文档格式真源：已明确，需修正 P0 标签并强化结构版本探针

更新稿已明确：workbenchDocuments.contentJson/documentSessionPort 是既有文稿真源，成果视图引用 documentId，不复制正文；Markdown 是交换格式；不能另写 Markdown 再反向同步。这已经解决“格式真源不明确”的主体问题，无需另建版本化 ProseMirror 文件仓库。

P0 的“一份 Markdown 文档”仍建议改成“一份已有原生文稿（可由 Markdown 导入）”，避免读者把它实现为 Markdown 文件成果。更重要的是，方案承认现有 revision 使用 updatedAt、hash 取派生纯文本，不能覆盖全部结构变化；这一点应提升为 P0 阻断项，而非普通核验提醒。至少验证：文字不变但标题层级、列表结构、marks、链接或图片属性变化后，旧候选不能提交；快速连续提交不会复用同一 revision；撤回再编辑也不出现版本身份碰撞。修改应在原 owner/提交边界补齐结构版本合同，不能用新增成果账本绕过。

HTML 的真源与 DOM 预览区别、Office 两种输入路线已比较清楚；后续应让按类型引用合同显式表达其 owner/source 类型，而不是依赖调用者猜测。

### D. 通用能力重复自写：方向合格，实施还需可审计的阻断点

第 7 节的“不自研”列表充分，没有把通用引擎包装成领域能力。但候选发布、command id、恢复、评论存储和跨版本映射目前多以目标行为描述。若现有框架没提供，不能默认由本切片补一个通用框架。建议 P0 把缺口分成“公共 API 可直接满足/最薄适配/必须另行选型”三类，只有前两类进入 M1；第三类先减范围或评估现成底座。

### E. 批量范围与撤回仍有组合边界

同版本多修改“构成一个候选事务”，不同成果逐项提交且可部分成功，与“以一次用户修改批次为单位撤回”存在待定义的组合语义。若用户一次提交两个成果，第一项成功、第二项失败，撤回是否回退全部成功项？若成功项之后又被人改过，不能直接切回旧引用覆盖新工作。

建议首版把原子/撤回单位限定到单份成果的一次提交；跨成果批次作为若干子提交显示，可逐项撤回。若保留跨成果一键撤回，就必须逐项期望版本检查与部分撤回回执，不得承诺全局原子。

### F. 少数候选承诺需要谨慎命名

“原位置显示改动标记”“按原位映射恢复反馈展示”“command id 幂等”仍是建议能力，文中未冒充已实现，但实现验收须逐项落实；删除目标后没有原位置时应转到线程/历史视图，不强求原位显示。性能 p95 与成本已标待测，Office 与平台也分开验收，这些边界表达充分，无需再加泛泛风险免责声明。

## 建议的最小修订顺序

1. 统一“未提交候选 / 已应用待验收 / 已验收 / 已撤回”语义，确认按 revision 记录。
2. 补一句“锚点跟随不延长写入授权”，写清跨重启映射缺失时保守失效。
3. 将 P0 改称已有原生文稿，并把格式/结构变更和连续提交的版本唯一性列为阻断探针。
4. 给 P0 单独出口表，并把 owner 落点、最薄适配清单、真实 Electron 证据列为必要产物。
5. 明确单成果与跨成果批次的提交/撤回粒度；补 Run 来源快照与后续成果修订关系。

上述修订不改变推荐方向，也不要求首版扩格式。结论仍是：可进入 P0 技术与交互探针；M1 开工前需把这些边界写成可验收合同。

### OpenDesign 对复用与 M2 的影响

新增 OpenDesign 已改变方案，而非仅增加一段项目介绍：第 3.6 节列出评论合同、锚点纯函数、受限 HTML 补丁、编辑桥等具体可摘取模块；第 4.1 节将其接到已有 TargetRef、owner、版本门与撤回。保留 React Flow/Tiptap/pi，不整体迁移上游应用，不把上游客户端预检查当服务端 CAS，不把路径标识当永久身份。没有发现要求先自研一套完整评论/锚点框架的残留指令。

M2、组件表和类型锚点表均以 HTML slides 为修改真源、slideId/元素 id 定位、dom-to-pptx 导出。明确不先造 SlideModel 或布局引擎；PptxGenJS 退为确需原生数据对象或截图输出的条件选项，且不得变成竞争真源。表格仍用 Univer 原生数据，没有因 slides 改为 HTML 就把所有成果一律压成 HTML。

导出限制也足够明确：可编辑 PPT 对象范围有限，复杂背景可能栅格化，SVG 的 Convert to Shape 不等于原生数据图表/表格；界面与服务端默认导出模式不同，版本升级与 PowerPoint 实际表现均待验。这些是方案中的源码调研结论，本报告没有独立验证。

OpenDesign 的 needs_review 状态与界面只显示 open pins 的区别属于新增研究边界补充，不以该句尚在补充阻断本次方案复查；也不能仅凭存在枚举就宣称上游已完成用户审阅闭环。
