# 类根因复盘（RW）：文本流「首字闸」把思考中的模型当死连接

> 触发：`node scripts/fix-churn.mjs electron/ai/streamTextTask.ts` 命中——文件近 14 天已有 4 个 fix，这一刀是第 5 个；自写登记 `ai-sdk-text-stack`（to-replace）近 30 天 5 个 fix，这一刀是第 6 个。
> 状态：用户 2026-10-21 已拍板（见「拍板」一节）：直接迁移，不打补丁。本文档随迁移线（分支 `refactor/text-tasks-pi-ai`，设计卡 `docs/plan/2026-10-21-text-tasks-to-pi-ai.md`）进仓库，不进 #1264。

### 0. 一句话根因

文本任务那一台 ai@4 调用栈把「判活」写死成「只数正文 token」，而思考型模型（DeepSeek V4、R1、o 系……）先吐 reasoning、正文很晚才来；判活口径和模型的真实行为不是同一份，所以每换一类模型 / 一条链路就冒一次。

### 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 2026-10-09 文本流停止 / 出错 / 超时都要让 await 收口 | ai@4 的流在 abort / 请求没发出时不 settle | 第二台调用栈的流生命周期要自己补 |
| 2026-10-11 拆解路径 429 不重试 | SDK 默认重试不区分 429 与 5xx | 第二台调用栈的默认行为不贴合领域 |
| 2026-10-21（本次）写作区 AI 编辑接 DeepSeek V4，30 秒后「首字未响应」，请求其实发出去了 | 首字闸只听 `textStream`（只含正文），reasoning 不算活 | 判活口径与模型行为不一致 |

### 2. 为什么会一直出现

第二台 LLM 调用栈（ai@4）和 lane 用的 pi-ai 是两套，流事件语义（正文 / 思考 / 元数据）各有各的处理，每个新链路接进来都要重新踩一遍。假桥演练里夹具回话立刻，永远测不到「想得久」，所以走查绿、真模型红——这是「假桥能过、真链路不通」那一类，铁律归属：⑫ 点了=以为的（用户点「缩短」以为在改，实际 30 秒后失败）。

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 其它走文本管线的功能（提示词优化、翻译、文本节点、拆解读图腿）接思考型模型同样 30 秒掉线 | `electron/ai/streamTextTask.reasoningLiveness.test.ts`（真 SDK + 本机假上游，先想后答） |
| 思考超过整体闸 120 秒的模型仍会被整体闸掐 | 同一测试把想的时长拉过整体闸 |

### 4. 靶子独立性

首字闸的「活」由同一条线定义，测试夹具此前也是同一条线写的立刻回话的假模型——靶子偏。已补一格「先想 35 秒」的夹具（`think-then-text`）。

### 5. P0

文本流判活、首字 / 整体超时、取消、重试都不是 Nomi 独有的。现成方案：lane 已在用的 pi-ai 单次调用（`electron/agentLane/laneSingleShot.mts:1`，登记条目 `ai-sdk-text-stack` 的 alternativesChecked 已列），计划 `docs/plan/2026-10-01-tech-stack-line-0.24.md`。**为什么现在换不了：** 文本任务栈挂着流式回调、取消、错误结构化、图片入参等一整套调用方（翻译 / 优化 / 文本节点 / 拆解），整体迁移是一条独立的线，不能塞进一个 fix。

### 7. 用户要权衡的核心

是现在先止血（一个小补丁，让写作区 AI 编辑能在思考型模型上用），还是等整条文本栈迁到 pi-ai 之后一起解决。

### 拍板（用户 2026-10-21，最终）

- 用户先选过「先 A 后 B」（先止血再迁移），随后改口：「我觉得迁移吧」——**直接做 B，不打补丁**。
- B = 文本任务整体迁到 pi-ai 单次调用；判活语义（正文与思考都算活、首字 / 整体闸、取消）在迁移里一次定义。
- 17 行补丁（`streamTextTask.patched.ts` / `streamTextTask.patch.diff`）**不提交**，只留作迁移线的参照；迁移完成时连整台 ai@4 文本栈（登记条目 `ai-sdk-text-stack`）一起删。
- 本目录里的测试与夹具改动是迁移线的**验收用例**：迁移后的文本栈必须通过 `streamTextTask.reasoningLiveness.test.ts` 同形的「先想后答不被掐 / 真死连接仍被掐」两条（测试要改成对新栈的入口），整机演练 `rehearsal.think-35s.diff` 里「先想 35 秒」那一格必须能过。

### 8. 系统哪里没拦住

- 登记表早把 `ai-sdk-text-stack` 标成 `to-replace`，但「要替换」没有日期、没有门岗逼它收敛，于是修补一直落在这份将被替换的代码上：10-09 两刀、10-11 两刀、10-21 第五刀。
- `fix-churn` 其实报过（「自写登记 to-replace，近 30 天已有 N 个 fix，先评估接入现成方案」），**修补线照样往下补**：门岗只打印、不阻断，派工的一方看到的是「这一刀很小」，看不到「这是同一个文件的第五刀」。
- 测试夹具与被测的判活口径是同一条线写的（假模型立刻回话），所以「想得久」这一类从来没进过测试——靶子不独立。
- 调用方矩阵从执行器往下测，入口之上的准入整层看不见：改写选区（#2）每次撞令牌付费闸、矩阵全绿，整机演练才暴露（走哪扇门由「给没给 onTextDelta」决定，不由任务种类决定）。补法：文本 kind 一律走流式门（结构）；真入口测试 `electron/ai/textEntries.ipc.integration.test.ts`；矩阵每个调用方登记真入口测试或缺口，渲染层发起的只许有测试（门岗，根因合同 `docs/fixes/2026-10-21-text-rewrite-routed-into-token-gate.root-cause.json`）。
- 独立验收三轮里失败留证的抹密修了 3 轮（F2）：第 1 轮只认固定鉴权头名，第 2 轮改成从实际请求收、按写法枚举回显变体，第 3 轮又被「按头名当公开」「等价编码不在枚举里」打穿。按 P1 停止补丁：「按头名猜秘密、按写法枚举变体」是类根因，抹密收成单一主人转 G-redact-owner（协调另线，方向交用户）；本 PR 只收敛到「不新增泄漏出口」——删掉本 PR 新加的「响应体进开发诊断」，日志不记正文。同一传输层的「每次尝试一份事实」（F1）与「断流有来源事实」（N1）是结构修法，留在本 PR。
- 补法（本 PR）：**删掉**（第二台调用栈与它的依赖整体删除，`import 'ai'` 编译即红）＞**门岗**（`check:llm-stream-owner` 改为「pi 单次调用唯一主人」：核心之外调 `streamSimple` / `stream` 即红）；夹具补「先想后答」「静默想」「断流」等真 HTTP 形状，按调用方逐个跑。
