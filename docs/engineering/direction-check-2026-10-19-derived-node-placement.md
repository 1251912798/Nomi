# 方向检查：派生节点落点按渲染占位避让（2026-10-19）

触发：`canvasGraphActions.ts` / `canvasNodeActions.ts` / `canvasStoreTypes.ts` 命中 `fix-churn`（近 14 天 6 / 6 / 8 个 fix，概念「画布分组交互」17 个）。这三个文件近 14 天的 fix 绝大多数是建边总闸、撤销、时间轴桥、分组删除——和「新节点落在哪」无关；落点这一线上一次动 resolveInsertionPosition 是 2026-09-25，再往前是 2026-06-14（卡片遮挡收口成唯一总闸、足迹余量统一）。本刀不是在同一处第 N 次补丁，而是把 6-14 那次「唯一总闸」里一直缺的那条边补上：总闸比的尺寸不是画面上真正占的尺寸。

### 0. 一句话根因

画布里同时有两种「节点多大」——名义 `node.size`（落点系统用）和渲染尺寸 `resolveNodeVisualSize`（所有几何子系统用）——总闸拿了前者，所以竖图、有媒体结果的卡一旦渲染得比名义大，新节点就合法地落进它们身上。

### 2. 为什么这一类会一直出现

06-14 那次把「不重叠」收成了总闸，但总闸的「尺」是一个固定外扩 64px 的名义尺寸——它吸收的是「渲染比名义高十几到几十 px」，吸收不了「宽高比决定高度」的媒体卡（9:16 的 320 宽图片渲染高度 ≈ 600，名义 180）。之后新增了越来越多「媒体到位后尺寸才定」的节点，每多一种，名义尺寸就更不是真相。缺的是：落点系统和几何子系统共用同一个尺寸来源。铁律 ⑩⑪⑫ 均不适用（不是 Agent 意图 / 模型档案 / 点击预期的问题）。

### 4. 靶子独立性检查

- 尺子是 DOM 实测：Electron 走查 `tests/ux/derived-node-placement.walk.mjs` 量的是节点在屏幕上的真实矩形，不是 store 里的任何尺寸；单测量的是 `resolveNodeVisualSize`（几何子系统共用的渲染尺寸），不是被测的落点系统自己的名义尺寸。
- 无「修对了反而掉分」的先例；旧测试（名义尺寸下的避让用例）全部保持绿，新规则只会比旧规则更严（按各轴取 max(名义, 渲染)）。

### 5. P0：这些是我们独有的吗？现成方案有哪些

落点避让是「画布节点怎么摆」的领域逻辑，属于我们独有（节点尺寸模型是 Nomi 自己的渲染规则）。`@xyflow/react` 只在节点渲染后才有测量尺寸，且没有「新建节点找空位」的工具；store 层创建节点时拿不到 DOM 测量，所以没有现成方案可接。`electron/capabilityCore/canvasNodeLayout.ts` 的布局数学本来就是共用的，本刀不改它的结构，只加 `newSize` 参数并删掉「返回没验过的最后一格」。

### 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 无适用的现成库（见第 5 节） | — | — | 不适用 |
| 补 | 在每个派生入口（拆解表、抽帧、剪辑……）各自加一段避让 | 每个入口一段 | 第 8 个入口又漏；与「唯一总闸」矛盾 | 否 |
| 重写（限一个模块） | 在总闸（`resolveInsertionPosition` 薄封装）里把所有盒子换算成渲染占位，新节点自己的占位也带进去；螺旋用尽落到所有节点下方；`addDerivedOutput` 不收 `exactPosition` | 小（一个封装 + 几行共享布局数学） | 低：只比旧规则更严；300 节点下多约 1ms | 是（已做） |
| 删 | 删掉派生节点「贴源旁边」的期望落点，全交给可见区落点 | 派生节点不再贴着源 | 丢了「新节点就在源旁边」的体验 | 否 |

### 7. 用户要权衡的核心

宁可新节点不贴在源右边，也不压住别的节点：源右侧放不下时，新节点换到最近的、真不压东西的空位（常常是源的下方或左下）。代价是节点密集时它不一定在右边（边缘有「新节点在…」提示，点了才过去，不动视口）。我们选「不压」。

**用户拍板（2026-10-19）**：选项「可以，宁可不贴右边（推荐）」——右侧拥挤时派生节点可以落在源的下方 / 左下，但绝不重叠。这条同时是本次方向检查的用户确认。
