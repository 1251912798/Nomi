# 方向检查：拖组框不跟手（P-dragframe）

> 触发：`node scripts/fix-churn.mjs src/workbench/generationCanvas/components/useCanvasSelectionDrag.ts` 命中「画布分组交互」概念（7 个文件，14 天 10 个 fix，这刀是第 11 个）；`components/` 目录 14 天 20 个 fix。
> 状态：用户 10-22 放行，按「换」做（协调转达）。

## 0. 一句话根因
拖动预览把「找目标」放在每帧里（`document.querySelectorAll` 按 id 拼出 241 个分支的选择器），因为 10-11 的 `f73fe2bc2`（成员壳与手柄跟着走）为了让预览不触发边重算，选了「直接改 DOM translate」，却没有在 pointerdown 时把目标解析一次并持有；缺的是「拖动预览的目标集合在手势开始时冻结」这一层。

## 1. 归类表
| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| f73fe2bc2 拖编组 / 选区时成员壳与手柄跟着走 | 预览改成改 DOM，选择器每帧现拼现查 | 手势预览每帧做全局查询 |
| 7920c29ec 选中一张卡画布壳 0 次重渲 | 同文件的性能修，没碰预览查询 | 同上（漏网） |
| 该概念其余 8 个 fix（拉环、建边总闸、浮层命中、顶栏居中等） | 分别在别的文件，与本次无关，只是共用同一个概念 / 目录计数 | 计数口径把「同目录无关 fix」算进来 |

## 2. 为什么会一直出现
概念计数是目录 / 概念级，本次要动的文件只有 1 个 fix（f73fe2bc2），其余是别的文件；但 GenerationCanvasReactFlow.tsx 等共享文件确实在反复被动。体验铁律：⑫ 点了=以为的（拖动手感）——本次无对应走查条目，不适用 ⑩ ⑪。

## 3. 不改结构会冒出什么
| 预测 | 验证 |
|---|---|
| 组框成员越多帧越慢（线性于成员数 × 全树节点数） | `pnpm run perf:scenarios` 跑 canvas-drag-group-frame，对比成员 20 / 60 / 120 |
| 选区拖动（`applySelectionPreview`）同样每帧查询，同类问题在另一条路上复发 | 同文件 133、145 行，门岗只数得到 1 扇门（`door-map`），但文件内有 4 处查询 |

## 4. 靶子独立性
尺子是 `tests/perf/canvas-scale-bench.mjs` 的 drag-group-frame-60 场景，不是本刀作者写的；基线 38.6 / 39.4ms（10-16，94724f860）是旧数，要在最新 main 上重测。量具注释里「每帧写 store」已不符合现状，需顺手校正。

## 5. P0
拖动预览手势是画布领域的自写，但「改位移」不是：React Flow 内核的节点拖拽本身就是持有引用后只改 transform。组框预览不走内核是有理由的（内核移动测量包装层会触发 ResizeObserver 重算全部连边，见源码注释），所以自写成立，只是没做到内核那样的「持引用」。

## 6. 对比表 + 推荐
| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 走 React Flow 内核拖动 | 触发每帧边重算，已被 f73fe2bc2 否决 | 退回更慢 | 否 |
| 补 | 保留每帧查询，缓存选择器字符串 | 小 | 查询本身才是 96%，不解决 | 否 |
| 换（限一个模块） | pointerdown 时解析目标元素并持有，帧内只写 translate；卸载 / 取消 / 结束时引用失效，settle 一次写回；同提交删 4 处 `querySelectorAll`（组与选区两条路一并换） | 一个文件 + 测试 | 节点中途被卸载要容错 | 是 |
| 删 | 去掉成员预览，只动框 | 成员不跟手，体验倒退 | 丢功能 | 否 |

## 7. 用户 / 协调要权衡的核心
这刀是「换」不是「补」（删掉每帧查询，不加分支），且其实际改动文件只有 1 个近期 fix；问题是按规则它撞了概念级的热点计数，是否放行按「换」来做。
