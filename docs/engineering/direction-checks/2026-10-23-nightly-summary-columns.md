# 方向检查：夜跑汇总按「构建 / 环境 / 产品」分栏（F-nightly-build-gate PR-2）

> 触发：`node scripts/fix-churn.mjs scripts/nightly-walk-summary.mjs` 命中「验证分档」概念（3 个文件，近 14 天 3 个 fix，这一刀第 4 个）。文件本身不热，只因概念登记命中；改法是「换」不新增分支，按例外由协调代批、事后报用户。

## 0. 一句话根因

夜跑汇总把所有失败当成同一种东西平铺成一张列表，没有「谁的问题」这一层，也没有整体失败的阈值，所以统一性的构建门失败（10-22 的 292 条）和常年 130 多条的环境 / 产品红混在一起，没人看得出性质变化。

## 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 夜跑自 10-08 起没绿过 | 汇总只有「失败列表」，没有分类、没有基线 | 失败没有归属栏 |
| 10-22 335 条挂 307 | 292 条是构建门拦截，和其余 15 条同列 | 同上 |
| 近 14 天该概念的其它 fix（验证分档、门岗） | 各自不同，只因登记在同一概念下命中 | 与本题无关，不是同一类 |

## 2. 为什么这一类会一直出现

汇总的唯一产出是「通过 / 失败」二值。任何新增的统一失败都只会让失败数变大，不会让人看到「这是 job 没跑」还是「产品坏了」。这不是某处少一个判断，而是汇总的数据形状里没有「归属」字段。

铁律对照：不适用（CI 内部汇总，不涉及意图抽取 / 模型选项 / 点击预期）。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 下一次共享启动边界的统一故障又被当成「普通红」 | `scripts/nightly-walk-summary.node-test.mjs` 的 10-22 形状夹具：改后 292 条归构建栏并整体红 |
| 环境红永远占 100+ 条，新回归埋在里面 | 同文件环境特征表夹具：每个特征都归环境栏 |

## 4. 靶子独立性检查

尺子是夜跑退出码本身，汇总只负责分类展示，不改判定。分类特征来自 R-nightly-broken 对 10-22 日志的实测，不是同一条线自证；分类错了只影响归栏，不会让失败变成通过。

## 5. P0：这些是我们独有的吗

不是独有。分类 / 阈值是通用 CI 汇总；GitHub 的 job summary 与 issue 已有，不加依赖、不发外部消息。环境特征表是我们对自己走查失败形态的登记，属领域登记数据。没有看到比 `gh issue` + job summary 更省的现成件（Actions 本身没有「按日志分类失败」能力）。

## 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | GitHub job summary + issue（已在用）；无现成「按日志归类」能力 | 0 | 无 | 已在用 |
| 补 | 在平铺列表上再加一段分栏统计 | 小 | 留两套并行呈现，违反 P1 | 否 |
| 换 | 平铺失败列表换成三栏分类 + 整体阈值，旧平铺同提交删；通过的只计数 | 中 | 日志缺失时分类不准（归产品并标「无日志」，不吞） | 是 |
| 删 | 不汇总 | — | 回到没人看见 | 否 |

## 7. 用户要权衡的核心

阈值（失败率 > 20% 或 > 30 条）宁可早醒、不要漏醒；常量导出可调，初值不准就改常量，不用动结构。
