# 方向检查：模型可见工具面反复修补（#1263-r4）

触发：`electron/shared/agentCapabilities/verbs/writeVerbs.ts` 近 14 天第 4 个 fix；同目录近 14 天第 9 个 fix。当前这刀是恢复被压短的 `stage_shot` 描述并补 `read_selection` 用例，不新增产品分支；结构性结论交协调会话拍板。

## 0. 一句话根因

模型可见工具的语义描述、效果组裁决、发布数量和预算由不同文件分别维护，新增一个动词或改一句描述就会在另一道门岗留下漂移；修复只能反复回填热点声明文件。

## 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| #1263 合并后 `check:tool-face` 两处 `[mutual-tiebreak]` | `stage_shot` 描述被压成短句，删掉两个同组互斥动词 | 同一效果组的裁决没有结构化 owner |
| #1263 合并后 `check:agent-tool-face-usecases` | 新增 `read_selection` 只改注册表，清单和硬编码数量未同步 | 发布注册表与评测清单各写一份 |
| #1263 合并后 `check:model-schema` | 新工具加入完整常驻组合，预算策略仍假定所有组可同时驻留 | 工具可见面与预算处置没有同一策略边界 |

## 2. 为什么这一类会一直出现

`VERB_DECLARATIONS` 是唯一发布真相，但 `notWhen` 仍是每个声明里的自然语言，usecase manifest 又有一份手写 canonical list，预算门岗则把所有组重新拼成最大组合。它们都能独立通过类型检查，只有合并后才暴露关系漂移。类根因落在铁律 ⑪「能选到」：模型看到的工具集合、互斥选择和评测题库没有由同一个可生成的关系表覆盖。铁律 ⑩ / ⑫ 不适用本次文档和门岗修复。

## 4. 靶子独立性检查

三道门岗都由脚本从注册表投影后独立计算；`check:tool-face.node-test.mjs` 的互斥阳性 / 阴性夹具不依赖 `writeVerbs.ts` 的实际文案。当前修复只恢复 main 的已审查描述并补一条真实用户句子，不能证明预算 / residency 方案已选定。

## 5. P0：这些是我们独有的吗

工具如何互斥、何时延迟披露、哪些用户句子代表真实工作流，是 Nomi 的 Agent 领域合同；没有现成库能替代 `VERB_DECLARATIONS` 与本地 lane 预算关系。JSON schema、MCP 分页和 pi 工具执行继续接入现成实现，不自写替代品。

### 自写登记 `gate-family` 的接入评估

`gate-family` 记录的是 Nomi 自有的模型可见工具声明、按组 residency、usecase 题库和仓库门岗之间的发布关系。通用 JSON Schema / MCP / pi 实现只提供单个工具的 schema 或执行协议，没有“同一声明同时生成多道本地门岗签名并按 Nomi 的内部 profile 计预算”的标准关系投影，因此当前没有成熟现成库可以接入而不引入第二份真相源。继续保留本地登记和脚本门岗的领域约束理由是模型面顺序、互斥裁决和预算阈值都属于 Nomi 的交付合同；本轮只删除废弃的 `read_selection` 路径，没有新增 gate-family 分支。协调在工具分组按需加载方案落地后、**2026-11-15 前**复查一次是否能把关系投影下沉到现成标准或生成器；在此之前不得为接入而扩大本 PR 范围。

## 7. 用户要权衡的核心

是继续接受「新增一个工具就同步三张清单」的低成本局部修补，还是先拍板 coding read/write 的模型可见面，再把发布关系和预算收成一个可生成边界；后者一次性改动更大，但能停止同一热点的循环修补。
