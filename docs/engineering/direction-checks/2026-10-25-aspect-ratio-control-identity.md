# 方向检查：比例控件身份与等价比较

### 0. 一句话根因

比例控件的身份和比例相等关系散落在键名别名、组件 Set、目录 binding 和字面字符串比较中，任何新模型只要换一个键名或用像素档就能绕开规则。

### 1. 归类表：bug → 直接原因 → 类

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| 清晰度选项误改比例 | `size` 被按键名当作比例控件，清晰度选择写入空比例并打显式标记 | 参数控件身份多份定义 |
| 像素档不随输入切换 | `1280:720` 与 `16:9` 按规范化字符串比较，没有约分等价关系 | 比例等价比较多份定义 |
| 连线目录与派生顺序尾巴 | 模型清单和派生顺序缺少回归钉子 | 共享边界缺少类级测试 |

### 2. 为什么这一类会一直出现

比例是领域语义，供应商键名和选项格式却是外部表示。当前代码一部分按键名猜（`size` 在 Agnes 是清晰度，在其它模型可能是比例），一部分按 binding 猜，一部分按 `normalizeAspectRatioToWH` 的返回字符串比；这些表示层规则没有统一的语义边界。新增模型只需出现 `1280:720` 或将清晰度命名为 `size`，就能让一个调用者误判而其他调用者仍正常。类根因落在铁律 ⑪：档案控件清单没有由单一语义判据自动覆盖所有入口；也落在铁律 ⑩：用户期望的 16:9 与草稿中的 1280:720 没有确定性等价比较收据。

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 新的 `ratio`/`image_size` 清晰度档会被误标比例 | 加一个非比例选项类级夹具，跑参数面板变更测试 |
| 新像素档比例会继续无法响应竖图输入 | 全目录普查中加入未约分像素值，检查 16:9/9:16 落档 |
| 另一个入口会恢复按键名判断 | `rg ASPECT_RATIO_KEY_SET ASPECT_RATIO_ALIASES` 并由静态审查门拦截 |

### 4. 靶子独立性检查

现有测试由实现线维护，但类级普查同时读取共享语义函数和档案目录，能发现“只改例子”的退化；变异测试在 git archive 副本中替换实现后必须出现红格。没有发现评测 oracle 被产品实现反向调用的证据。

### 5. P0：这些是我们独有的吗？现成方案有哪些

比例值解析和约分比较是通用数据处理，可由现有 shared 工具承载；真正独有的是 Nomi 的“视频首选 16:9、仅全竖输入改 9:16”规则和供应商原值保留，这部分必须留在领域边界。没有引入新依赖。

### 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 继续复用现有 `parseAspectRatioValue` / `optionsAreAspectRatios` | 需要定义 shared 语义接口 | 只能覆盖解析，不能表达首选规则 | 次选 |
| 补 | 在 `aspectRatioValue.ts` 增加唯一 meta 键表与约分比较，所有入口改导入 | 改动集中，需迁移旧引用 | 未删旧判断会继续漂移 | **推荐** |
| 重写（限一个模块） | 重写参数模型的全部控件判断 | 局部简单但会留下组件/宿主重复 | 其它入口仍可回归 | 不推荐 |
| 删 | 删除比例默认派生或让供应商自决 | 失去用户拍板的连线默认体验 | 花错比例 | 不采用 |

### 7. 用户要权衡的核心

收口会删掉少量本地别名和按键名便利，但换来所有模型和入口都由同一个语义判据决定，代价是以后必须给异常档位补共享测试而不是局部特例。
