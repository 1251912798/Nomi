# Agent 权限挡位：类根因复盘（方向检查，RW）

> 触发：`node scripts/fix-churn.mjs src/workbench/ai/v4/agentPanelV4Types.ts` 报「近 14 天已有 5 个 fix，这一刀是第 6 个」，`electron/settings/` 目录报第 3 个。
> 这一刀不是第 6 个补丁：用户（2026-10-12）说「挡位这个地方有问题啊 相当于没有挡位」，拍板把三档**换成**两档。下面是对「为什么这里一直在补」的类根因说明，结构性结论已由用户拍板（见 §7）。同一概念的后续提交共用本文。

## 0. 一句话根因

「用户选的挡位」和「系统此刻到底问不问」没有一个单一的可读答案：三档词表、一根没有读者的 `spend` 轴、两个互不相同的判据函数（工具审批 `capabilityMayReuseSafeApproval`、付费代答 `spendDecidedByPolicy`）各管一半，于是「每步问」与「自动改」在花钱 / 不可逆上行为完全一样（用户感受到的「没有挡位」），每次改其中一处就要在另外几处补注释和测试。

## 1. 归类表

| 提交 / bug | 直接原因 | 类 |

## 2. 为什么这一类会一直出现

档位是用户的授权声明，但它被拆成「模式」和「花钱」两根轴，再被各调用点各自按自己的需要解读；每新增一个调用点（lane 工具审批、外部 MCP 门、接入试跑、Run 信任档）就多一份解读，改任何一处都要同步其它几处的注释。带 Run 的付费代答还没有任何「不该替用户续跑」的事实可依据（连续失败、计划外），所以「全自动」只能是全开或全关。

三条铁律：⑫「点了 = 以为的」——用户点「每步问」以为会更谨慎，实际与「自动改」在花钱 / 不可逆上无差别；本类的类检查是放行矩阵测试 `electron/shared/agentCapabilities/capabilityApprovalTwoTiers.test.ts`（可撤销 / 花钱 / 不可逆 × 两档，每格唯一答案）。⑩ ⑪ 不适用（无参数 / 模型选项）。

## 4. 靶子独立性检查

放行矩阵与刹车的断言读的是纯函数结果与真实 Run 夹具（`jobsForShot` 派生），不复述实现；迁移用例读盘上旧格式的字节。第一轮必红测试与实现不是同一次提交，且上一轮已由协调会话审过；不存在「修对了反而掉分」的先例。

## 5. P0：这些是我们独有的吗？现成方案有哪些

「按镜头的花钱语义」「已经说好的计划」「同一镜连续失败」属于领域目录（`docs/engineering/self-written.json` 的分镜 / 制作流程 / 按镜头花钱），自写合理；挡位切换确认复用现有介入槽，没有新组件。通用部分（持久化设置文件）已经复用 `configFileStore` 原语。没有可接入的现成「权限挡位」库：行业里（Claude Code / Codex / Cursor）的审批模式都是编辑器内文件操作语义，不含按镜头花钱与连续失败刹车。

## 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 无适用的库（见 §5） | — | — | 否 |
| 补 | 在三档上加刹车、给「全自动」加说明 | 保留没人要的「每步问」和没有读者的 `spend` 轴 | 用户依旧觉得「没有挡位」，第 7 个补丁 | 否 |
| 换（本分支） | 两档 + 单一入口 `spendDecisionByPolicy`，旧三档同提交删，盘上旧值一处迁移 | 约 60 个测试 / 夹具文件的词表改写；几条真机走查需改触发方式 | 迁移与词表联动 | 是 |
| 删 | 去掉整个挡位 | — | 用户明确要两档 | 否 |

## 7. 用户要权衡的核心

用户已拍板（2026-10-12）：要两档——「请求批准」和「直接生成」，直接生成只在同一镜头连续失败、或超出说好的计划时才停；旧值全部落「请求批准」。

## 补记（2026-10-16，独立验收 V-1203 之后）

`fix-churn` 对 `electron/capabilityCore/modelOnboarding/tryModel.ts` 报「14 天第 4 个 fix」。这一刀不是给试跑打补丁，是**删掉一条旁路**：试跑原来直接问档位那一半（`spendDecidedByPolicy`），现在和另外两扇门一样只问唯一代答入口 `spendDecisionByPolicy`（无 Run 时只剩档位那一问，行为不变）。协调拍板「统一走同一个入口，不另开旁路」。结构上的拦截：`directGenerationBrakes.boundaries.test.ts` 扫 `electron/` 生产代码，除入口自己与不付费的放行矩阵外，谁再直接问档位那一半就红。同一轮还修了两处同类问题（刹车判据从派生状态推、而不是从历史事实推）：「说好的计划」改取曾有 job 的镜（去掉的也算），连续失败从上一次人批之后数（人批读付费门 → 出价 → 谁决定的事实），最近一次没到过供应商的失败不再让刹车失明。

复验 R2（同一方向内的最小修复）：人批的那次尝试若提交前没写出去，原来的回溯先跳过了「没写出去」、根本没看到这次人批，于是继续拿批准前的失败拦人（多问一次，不越权）。改成：没写出去的失败照旧不计不重置，但它若是人批的，就在这里停——人批本身是计数的起点。
