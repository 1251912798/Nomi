## 0. 一句话根因

同一镜头有三个家（Agent 候选、卡自己的账本、画布节点）、两台发动机（卡上确认走 Agent 路，节点 ↑ 走画布路），每多一个用户可选的维度，就要有人记得在几处投影、几处回写、两条发出路径里各补一次。缺的是「镜头只有一个家、花钱只有一条路」这一层。

## 2. 为什么这一类会一直出现

结构层：卡是候选的一份可编辑副本，节点是候选的另一份投影，二者都能被改、都要同步；确认时花钱的是 Agent 路（读候选），节点 ↑ 花钱的是画布路（读节点）。所以「卡上看到的 = 节点上的 = 实际发出的」要靠每个维度三处投影 + 两条发出路径各自对齐，任何一处漏写都不会报错。

三条体验铁律：⑩「说的 = 摆的」——适用：起草写下的模型 / 变体 / 比例 / 时长 / 参考必须逐项等于节点、等于发出（本线把它做成对等矩阵的常驻一维）；⑪ 不适用（不改档案清单的生成方式）；⑫「点了 = 以为的」——适用：点「生成」的预期是「按节点当前参数发」，实际结果由假上游抓的真请求体证明。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 档案再加一个用户可选维度（例如张数），卡上能改、节点上没有，确认发出的和节点 ↑ 发出的不同 | 对等矩阵新一维（起草 → 节点 → 显示 → 发出），新维度不进投影表就红 |
| 用户在节点上改了时长，再在卡上点确认，发出的是候选里的旧时长 | 同上，「改过」那一档 |
| 直接生成档与节点 ↑ 走的不是同一条路，同一镜头两种按法发出的参数不同 | 同上，参考方式格 |
