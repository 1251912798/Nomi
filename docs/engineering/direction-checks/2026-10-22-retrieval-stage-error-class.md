# 方向检查：取回阶段的错误说成「还没发出去 / 可以重试」（⑬）

> 触发：`node scripts/fix-churn.mjs` 命中——`electron/tasks/taskResultQuery.ts`（文件 14 天第 4 个 fix；`electron/tasks/` 第 16 个；概念「异步生成结果取回」第 20 个）、`electron/shared/nomiErrorCodes.ts`（第 4 个）。来源：`docs/engineering/direction-checks/2026-10-22-poll-reupload.md` 2b 节，用户 2026-10-22 拍板另开 PR 修。设计卡与验收清单：`docs/plan/2026-10-22-retrieval-stage-error-class.md`。

## 0. 一句话根因

错误码自带「请求发没发出去」的语义，却没有一个地方写下「每个码属于提交前还是提交后」；取回链的出口（主进程 `retrievalStageError`）和渲染层的唯一分类器（`classifyGenerationError`）都没有按阶段把关，于是提交前语义的码能从取回阶段冒出来，取回阶段的码在渲染层又被当成「认不出 → 重试」。

## 1. 归类表

| 提交 / bug | 直接原因 | 类 |
|---|---|---|
| #1213 一批（10-16，结果误选、状态词表、取回阶段码） | 取回阶段没有阶段码，失败一律含糊 | 引入了 `retrieval-*` 码与「可找回」去处——解决的是「取回失败说不清卡在哪」 |
| 出站守卫分家（`outbound-blocked` / `-submit` / `-credential-origin`） | 同一个码在提交侧和取回侧口径相反 | 生产者按阶段分家，但 vendorHttp 那一层不知道这次请求是查询，一律按提交挂码 |
| #1285（本日） | 查询前重传参考失败挂 `asset-upload-failed` | 同上：提交前语义的码从查询链冒出来 |
| 本次 | `retrievalStageError` 放行任何已带码错误；分类器没有 `retrieval-*` 分支 | **码的阶段没有 owner**：生产者不知道阶段，出口不按阶段把关，读者不认阶段码 |

不是前面那批的第 N 刀：前面收口的是「有没有阶段码」「出站守卫分家」，这次补的是「码和阶段的对应关系」本身。

## 2. 为什么这一类会一直出现

阶段是按「谁抛的」来定的：`asset-*` 是素材本地化抛的，`outbound-blocked-submit` 是 vendorHttp 守卫抛的，而这两个生产者都被提交和查询共用，它们不知道自己在哪个阶段。真正知道阶段的只有两处：主进程的取回出口 `fetchTaskResult`，以及渲染层「提交成功之后」那段代码。这两处今天都只认「有没有码」，不认「码属于哪个阶段」。

铁律对照：⑫「点了 = 以为的」。用户点「重试」以为是重查，实际是再生成、再扣一次。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 查询时代理 fake-ip 未确证 → 可找回面板印出「这次生成没有发出去……然后重新生成」 | C1 / C5 特征测试 |
| Agent 面板 / 分镜格对取回失败给「可以重试一次」 | C4 分类器单测（实测：`retrieval-query` → `unknown` + `retry`） |
| 以后新加一个提交前语义的码，同样从查询链漏出去 | C3：阶段表穷举，新码不写阶段 typecheck 红 |

## 4. 靶子独立性检查

- 判据来自用户拍板的原则（取回阶段不说「没发出去 / 可重试」）与既有码表注释，不是本线自定。
- 无「修对了反而掉分」先例。

## 5. P0：这些是我们独有的吗

错误码的阶段语义、「可找回」去处、按镜头的花钱语义都是我们自己的领域，没有现成库。

## 6. 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | 无对应库 | — | — | — |
| 补（推荐） | 码表加穷举阶段表；`fetchTaskResult` 出口统一改挂提交前语义码、无码错误包成取回码；分类器认 `retrieval-*`；渲染层「提交成功之后」的错误一律落可找回 | 码表 + 两个出口 + 分类器一支 | 低：只改取回阶段的说法与去处，提交阶段一字不动（C10 守） | ✅ |
| 改生产者 | 把阶段一路传进 vendorHttp / 素材本地化，让它们自己挂对码 | 改动面大（vendorHttp 是所有供应商请求的出口） | 中：每个新生产者都得记得传阶段，漏一个就回来 | 以后 vendorHttp 拆分时顺带做 |
| 删 | 去掉提交侧专用码 | — | 高：提交阶段确实需要「没发出去」那句话 | ❌ |

## 7. 用户要权衡的核心

在取回出口统一改说法（一处把关，生产者不用改），还是把阶段传遍所有生产者（更「正」但面大、容易漏）。本线按前者做，阶段表让新码自动被管住。
