## 0. 一句话根因

「项目库列表」这个**共享读面**被我们塞进了**一个消费者的展示策略**（「零编辑空白草稿不显示」），而它有五类消费者，各自默认「列表 = 所有登记过的项目」。往前追同一类：「一个项目在不在库里、处于什么状态」没有唯一主人。列表、启动发现、删除、界面确认框各自推断，每修一处，就有另一处的推断和它不一致。

## 2. 为什么这一类会一直出现

**复现**（本机，隔离资料）：
- `node tests/ux/golden-path.e2e.mjs`，以及 real-user-journeys 里的 `tests/ux/resident-composer-receipt-fix.e2e.mjs`，都在同一处红。
- 位置：`tests/ux/agent-runtime-walk-support.mjs:513`，报错 `The real created project must have a canonical isolated folder`，`Received: undefined`。
- CI 上 real-user-journeys 的 3 条红（agent-real-user-conversation、agent-transcript-merge、resident-composer-receipt）全是这一行，golden path 也是这一行。

**机制**：
- 新建空白项目时 `createLocalProject` 打上 `draft: true`，revision 是 0。
- 本 PR 的 C′ 共用部分让 `listWorkspaceProjects` 把「能证明为空的草稿」藏掉了。
- 用户还在这个项目里、还没保存，它就从列表里消失了。

**列表的读者**（door-map 数过）：

| 读者 | 位置 | 默认的含义 |
|---|---|---|
| 项目库界面 | `localProjectStore` → `listLocalProjects`（`projectRepository.ts:124`） | 要展示的卡片 |
| 全部项目的素材 | `useAllProjectAssets.ts:159` 的 `listAsync` | 所有项目 |
| MCP / 外部 Agent | `capabilityCore/core.ts:136` 的 `listAllProjects`，经 `dispatcher.ts:355` | 所有项目 |
| 工作流来源名 | `workflowLibrary.ts:122` | 所有项目 |
| 走查与脚本 | 13 个 `tests/ux/*` 加 `scripts/sweep.mjs`，用 `listAsync` 找 rootPath | 所有项目 |
| 顶栏最近项目 | `ShellTopBar.tsx:78` | 排除当前项目 |

只有第一个读者想要「藏空草稿」，其余五类都要「所有登记过的项目」。

**入口**（door-map 数过）：
- **新建**有 4 扇门：
  - 渲染层 `createLocalProject`（`NomiStudioApp.tsx:455`），只有空白新建会打 draft；
  - MCP `createNamedProject`（`core.ts:140`），不打 draft；
  - 打开文件夹（`workspaceIpc.ts:214`），不打 draft；
  - 示例 / 引导，带 seedKey，不打 draft。
- **打开**：按 id 读（`readLocalProjectAsync` 等 3 处），不经列表，不受影响。
- **列举**：只有 `listProjects` 一个主进程读面，加上启动发现 `discoverLegacyProjects` 这一个「成员推断」入口。

**为什么每修一处就冒一处**：
- 成员资格（在库里吗、能读吗、能删多少、要不要展示）没有一份唯一的事实。
- 列表、启动发现、删除、确认框各自从「登记 + 盘上文件 + 清单字段 + 标记文件」里推断。
- 本 PR 每一轮改的都是其中一处的推断，另一处的推断就和它对不上：
  - 删除的推断对不上界面的推断（r1）；
  - 启动发现的推断对不上移除的推断（r2）；
  - 列表的展示策略对不上其余读者的含义（本轮）。

**三条体验铁律**：⑫「点了 = 以为的」适用。用户新建项目后回库能不能看到它，取决于离开时那一次整存；离开路径一变（A 项「离开只写欠着的」），刚建的项目就会从库里消失。⑩ ⑪ 不适用。

## 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |
|---|---|
| 只给「当前打开的项目」开豁免：MCP 在用户刚建的空白项目里干活时，用 `nomi_project_list` 选项目照样找不到它；`useAllProjectAssets` 漏掉当前项目 | 新建空白项目不保存 → 走 MCP 列表 / 打开「全部项目素材」 |
| A 项（离开只写欠着的）落地后，没动过的空白项目一回库就消失。如果那时用户在里面导入过素材但还没触发保存，就是「我刚建的项目不见了」 | A 项分支上跑「新建 → 导入一张图 → 立刻回库」 |
| 启动发现按「已移除标记」和「登记」两套来源推断，被移除的外部文件夹或老项目还会以别的形态回来 | 移除一个根目录带旧版 project.json 的外部文件夹 → 改名 → 重启 |

## 6. 选项

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| A 继续修 | 列表照样藏空草稿，但给「当前打开 / 本会话新建 / MCP 绑定」的项目开豁免 | 小，约 20 行 | 第三个特例分支（P1 明令停）；预测 1、2 照样会来；豁免条件靠主进程猜「谁在用」 | 否 |
| **B 收窄本 PR** | 撤掉「能证明为空的草稿不显示」：`isProvablyEmptyDraft` 及其测试同一提交删掉。列表回到「所有登记过的项目」，和 main 的读者含义一致。N1（不再有删除器）、N2（逐项隔离）、删除照意图执行、启动发现隔离、取锁不造根都保留。再补一条读面合同测试：「每个登记过的项目都在列表里，读面不做展示策略」 | 小，约 −40 行，删 5 条测试、加 1 条 | 用户可见：崩溃 / 关机 / 强杀留下的零编辑空白项目会以「未命名项目」卡片出现在库里（main 上它们会在下次启动被回收删掉），用户可以自己删。只在「开着没动过的空白项目时崩溃」才会出现 | **是** |
| C 换结构 | 给「库成员资格」一个唯一主人：登记表里每项带状态（在库 / 已移除 / 读不出），列表是它的纯投影，启动发现只往登记里写；「已移除」记在设置目录的登记里，不再往项目的 `.nomi` 写标记；空草稿的去留并进 A 项，由项目自己的离开流程决定；界面「藏不藏」是项目库页自己的策略，读面只给 `draft` / `revision` 这些事实 | 大：改登记表 schema 加迁移，碰启动发现、删除、列表、界面四处；单独立项 | 动登记表格式，要旧数据迁移；和 A 项、回收站 ⑭ 碰同一扇门，要排队 | 方向上对，交用户，单独立项（建议和 A 项合并成一条线） |

**推荐 B**。理由：
- 这 3 轮暴露的是成员资格没有主人。这个结构问题不该在一个修 N1 / N2 的 PR 里继续长；
- 「藏空草稿」是 C′ 为了替代被删掉的回收器加的体验补偿，不是 N1 / N2 的必要部分；撤掉它，本 PR 回到可交付的最小正确范围；
- 读面合同测试把「读面不做展示策略」钉住，这一类不会再从列表这扇门回来；
- 崩溃残留卡片的整理，交给 C 和 A 项一起做。

## 7. 要用户权衡的核心

- 「项目在不在库里、显不显示」的统一主人（C）另开一条线，和「离开只写欠着的」一起做。
- 推荐先合 B。

## 系统哪里没拦住

- **实现和验收都没跑碰到项目新建的走查**：
  - 本线只跑了单测、门岗和自写的截图脚本；V-plibrary2 三轮也只跑单测和外置用例。
  - golden path、real-user-journeys 只在 CI 跑，推送前钩子也不跑。
- **改共享读面时没核读者**：
  - 本线 door-map 只数了写入口和读面本身，没把 `listAsync` 的 13 个走查读者算进去。
  - 根因合同模板的 `doors` 只要求数「写和读入口」，没要求「读面语义变化时逐个核读者的期望」。
- **补法建议**（强弱依次）：
  1. **结构**：B 里加读面合同测试「列表 = 所有登记过的项目」，语义改动在单测层就红。
  2. **门岗**：`scripts/validation-policy.mjs` 的路由，把 `electron/workspace/workspaceRepository.ts`、`electron/projects/repository.ts` 的列举 / 新建改动映射到「至少跑一条会新建项目的走查」（golden path 第一步就够），推送前或 `delivery:preflight` 时提示本机先跑。
  3. **规则文字**：root-cause-remediation 技能的 door-map 一步补一句「改了读面返回什么，就把这个读面的全部读者（含 `tests/ux` 走查）列进 doors 逐个核」。
- 本页只给建议，三条都等用户 / 协调拍板 B 之后随修复一起做。
