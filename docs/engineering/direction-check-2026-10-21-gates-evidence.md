### 0. 一句话根因

**批准范围是「默认放行」**：哪些变化需要协调确认，由「PR 自报的认领集合」加「一份我们列出来的要保护的字段 / 元素清单」决定——没列到的就漏，所以每补一处，都能从下一处没列到的地方绕过去。

### 2. 为什么这一类会一直出现

两轮的补法都是「在默认放行的基础上，再多列一个要拦的东西」：第 1 轮列政策字段（`POLICY_KEYS`）与元素合同字段；第 2 轮加确认记录。结构没变：判据读的是**「我们想到要保护的字段」**，而不是**「PR 实际改了什么」**。攻击者（或下一个实现线的无心之失）只要找到清单外的一处改动——删除、板级字段、没被认领的元素、没写拍板图节的清单改动——就绿。每个修补都正确，但集合是开放的，补不完；V-gates 两轮各找到 2 处，是同一个形状。

### 5. P0：这些是我们独有的吗？现成方案有哪些（登记条目 id：`gate-family`）

通用部分已看过：GitHub CODEOWNERS / 分支保护必需审批 / Rulesets、OPA / conftest（策略即代码）、`git diff` 整文件哈希（这一条是下面推荐方案的基础，无需新库）。
- CODEOWNERS / 必需审批判的是「某个 GitHub 账号批准」；本仓所有线共用同一个账号，分不出协调与实现线（领域约束）；
- OPA / conftest 能评估策略，但「谁批准了哪份内容哈希」要自己提供，替代不了批准记录。
所以批准记录（本机 JSONL + 内容哈希，已在第 2 轮实现）是我们独有的；要重新设计的只是**批准范围怎么算**。

### 6. 方案对比与推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| **A 默认全拦（结构改法）** | 合同文件（板文件、场景文件）**整份**对比 base 与 head；先剥掉白名单里允许 PR 自改的**实现进度字段**（板：元素的 `status` / `assertion` / `owner`；场景：`baseline` 的 `machine` / `date` / `commit`）；剩下的规范化内容只要有任何差异（新增、删除、板级字段、新字段）就要协调确认，哈希绑定**整份规范化后的内容**；要确认的集合由**真实 diff** 构造，不看 PR 认领了什么，认领只用来关联实现验收；场景的 `POLICY_KEYS` 反过来：除白名单外全算政策 | 删掉 `POLICY_KEYS` 与元素合同字段的列表，改成一份「允许自改的进度字段」白名单（更短、更稳）；协调确认次数上升（见基线负担） | 白名单写得太窄会误报，只会多确认一次（安全方向）；没有「漏」的方向 | **推荐** |
| B 拆分 | 把清单批准从 #1266 拆出去，先合已经过关的部分（独立验收报告判据、性能证据、B2 / B3、S 项）；清单批准另开 PR 按 A 实现 | 本 PR 的拍板图认领判据暂时没有「批准身份」这一层（回到第 1 轮之前的 B4 缺口，清单仍可自造），要在文档里写明未验证；多一个 PR 的往返 | 过渡期有已知缺口，靠协调人工看清单 | 备选（A 一时做不完时用） |
