# 方向检查：证据判「对不对」门岗（PR #1266 第 2 轮，自写登记 `gate-family`）

> 触发：`fix-churn` 命中自写登记 `gate-family`（近 30 天第 87 个 fix）；本线在 #1266 上第 2 轮修补（第 3 轮要停下复盘，所以这页先写）。

### 0. 一句话根因

门岗只检查「证据在不在」，没回答「这份证据谁批准的」：PR 能同时改**数据**和**判据读的合同数据**（性能场景预算、拍板清单），于是自己给自己开绿灯。

### 2. 为什么这一类会一直出现

判据代码取 base，但「数据」和「政策」混在同一个文件里（场景 JSON 既有描述、也有预算），一并被当成可扩充数据读 PR head。每补一处只拦住一种放宽形状。类根因落到「批准身份」：合同类数据的批准来源必须在 PR 够不着的地方——base，或协调在本机留下的确认记录（哈希绑定内容，内容变了记录失效）。

### 3. 不改结构的话，接下来会冒出什么

| 预测 | 怎么验证 |

| 协调懒得跑确认命令，改成放宽判据 | `merge-preflight` 没有记录就红，CI 只警告，不存在「设个变量就跳过」；记录绑 PR 号与内容哈希 |

### 4. 靶子独立性检查

- 判据由实现线写，复验由独立线（Codex V-gates）按反例对抗跑过，11 个历史 PR 回放验证无大面积误伤。
- 没有「修对了反而掉分」的先例。

### 5. P0：这些是我们独有的吗？现成方案有哪些（登记条目 id：`gate-family`）

通用部分已看过：GitHub CODEOWNERS / 分支保护的必需审批、Rulesets、OPA / conftest（策略即代码）。结论：
- CODEOWNERS / 必需审批判的是「某个 GitHub 账号批准」；本仓所有线共用同一个 GitHub 账号，分不出「协调」与「实现线」，这是领域约束；
- OPA / conftest 能评估策略，但批准来源（谁、对哪份内容哈希批准）仍要自己提供，它替代不了批准记录。

所以批准记录（本机 JSONL + 内容哈希）是我们独有的：协调会话与实现线的角色分工。

### 6. 接入 / 补 / 重写 / 删 对比表 + 推荐

| 选项 | 做什么 | 代价 | 风险 | 推荐 |
|---|---|---|---|---|
| 接入现成方案 | CODEOWNERS / Rulesets | 要先把协调和实现线分成不同账号 | 账号分离是组织决定，不是本 PR 能做 | 评复时再看（`gate-family` 的 reviewBy 2026-10-31） |
| 补 | 加协调确认记录，政策字段 / 清单合同由 base 或记录批准 | 协调每个有合同变更的 PR 多跑一条命令 | 协调忘记确认 = 红，不放行 | 推荐（本 PR） |
| 重写 | 一次性重做门岗族 | 大 | 超出本轮 | 否 |
| 删 | 删这三处判据 | 回到 #1264 的漏放 | 高 | 否 |

### 7. 用户要权衡的核心

合同类数据的批准身份由谁给：现在是协调的本机记录；换成 GitHub 账号分离会更强，但是组织层面的改动。
