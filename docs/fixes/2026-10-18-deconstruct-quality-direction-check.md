# 方向检查：视频拆解的产出质量（`electron/video/deconstructVideo.ts`）

日期：2026-10-18 · 触发：`deconstructVideo.ts` 14 天内第 3 个 fix（commit-msg 闸）· 现场：首次真付费效果评测 `evals/deconstruct/run.mjs`（apimart/gemini-3.5-flash，4 条登记真实素材，46 镜）

## 0. 一句话根因

拆解的「产出好不好」一直没有尺子：三次修补（10-11 读图腿可选模型 / 失败原话落表 / 429 不重试；本次运镜语言）全是用户在真机上撞见后才补，因为代码里只有单测和零花费夹具，没有任何东西拿真实素材、真实模型量过表里每一列。

## 2. 为什么这一类会一直出现

拆解是「一条视频进、一张表出」，表的质量只能在真实素材 + 真实模型上看出来；仓库里没有这样的量具，于是每个质量问题都要等用户在真机上撞。铁律落点：⑩ 说的=摆的——表头写「运镜」，用户期望一列中文说明，摆出来的是英文提示词。

## 3. 不改结构的话，接下来会冒出什么

| 换一个读图模型（如 moonshot / minimax）景别合规率掉到六档之外 | 同一量具 `--vision-model` 换模型对比 shotSizeValid |

## 4. 靶子独立性检查

尺子（metrics.mjs）只量用户看得见的东西（成功率、填充率、六档合规、语言一致、调用数 = 镜数、对白字错率对作者逐字稿），由单测钉住；参考答案（逐字稿）是作者自己的，不是实现线写的。

## 5. P0：现成方案

拆解本身是领域（`docs/engineering/self-written.json` 领域目录：分镜 / 镜头与制作流程）。评测框架层没有引第三方：指标是领域口径（六档景别、按镜对白），跑法复用仓库已有的付费走查设施（`tests/ux/_paidRun.mjs`、`tests/ux/fixtures/realMedia.mjs`），没有新写 harness。
