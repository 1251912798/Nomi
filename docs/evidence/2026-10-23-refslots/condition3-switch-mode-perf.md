# 条件 3：切方式（30 张参考，参考 → 首尾帧）慢在哪——剖析与三组交错 A/B

> #1269 合并前条件 3（验收报告 V-b1a-r3：「同时段 A/B 重写后慢约 25%，中位 112.5 → 140.8ms」）。
> 对照：重写前 = `4e8659fbf`（第 2 轮头，临时工作树，用完已删）；重写后 = `7930f8548`（本轮条件 1 / 2 / 4 已提交）。
> 机器：Apple M5（Mac17,2），10 核。整段**不空闲**：1 分钟负载 9–35，别的会话常驻 230–250 个 node 进程。
> 所以只做**同时段交错**比较（两边轮流跑，每批前记负载），不拿绝对数说事；预算 100 的绝对数见文末「没做到的」。
> 实验室状态 `b3r-video-30-refs`，真组件、无头 Chromium、开发构建（StrictMode 双渲染）。零网络、零额度。

## 结论

1. **用户感受到的响应时间：没有变慢。** 用验收线同一个量具（`tests/perf/composer-refs-bench.mjs --op switch-mode`，
   输入事件起表 → 判据到位再过两帧）交错 4 轮 × 5 次：配对差中位 **−0.1ms**，4 轮里 3 轮重写后不慢于重写前，长任务两边都是 0。
   这个量具按帧取整（两边都落在两帧 ≈ 32ms），只有机器很忙、主线程活多到跨过帧边界时才会显出差别——验收线那一轮 CPU 76–100%、每次切换带一个长任务，正是这种情况。
2. **主线程真多干的活：约 +2.5–3ms（约 +10%）。** 不按帧取整的量法（下面方法 2）4 轮全是重写后多：忙碌时长配对差中位 **+2.95ms**，点击处理（事件处理 + React 同步渲染）**+2.45ms**。
3. **多出来的几乎全是 ⑫ 的 ×（用户 10-22 拍板「未用到也能删」），不是参考推导。**
   切到首尾帧后生成框里的 DOM 节点：重写后 390、重写前 250，多 140 个 = 28 张「未用到」× 每颗 × 的 5 个节点（button / i / svg / path / path）。
   把「未用到」的 × 临时拿掉再交错量 4 轮：点击处理配对差中位从 +2.45 降到 **+0.2ms**。
   CPU 采样里参考推导（`resolveReferencePlacement` / `resolveGenerationReferences` / 必需模式 / 能否生成）每次切换合计约 0.4–0.7ms，重写前的对应推导约 0.5ms，差 0.1–0.3ms——
   验收线猜的「三处各算一遍推导」不是时间的去处，给它加缓存省不出可量的东西，所以**没加**（剖析证据不支持的优化不做）。

## 方法 1：验收线同一个量具，交错 4 轮 × 5 次

`ab.sh`：每轮先重写后、再重写前，各跑 `composer-refs-bench.mjs --op switch-mode --runs 5`（每次全新页面，第 0 次热身不计）。

| 轮 | 1 分钟负载（后 / 前） | 重写后中位 | 重写前中位 | 差 |
|---|---|---|---|---|
| 1 | 21.1 / 19.1 | 32.3 | 32.2 | +0.1 |
| 2 | 19.0 / 20.9 | 31.8 | 33.7 | −1.9 |
| 3 | 28.9 / 25.0 | 32.1 | 37.7 | −5.6 |
| 4 | 23.0 / 19.4 | 32.1 | 32.2 | −0.1 |

配对差中位 −0.1ms；长任务 0 / 0。计划里定的判据（配对差中位 ≤ +3ms、4 轮里至少 3 轮不慢）成立。
